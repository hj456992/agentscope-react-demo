# 集群执行差距评估

日期：2026-11-02

评估对象：`docs/集群环境部署改造方案.md` 与当前 `outputs/demo/demo` 代码。

结论：当前系统做到了“单进程异常后可恢复”，还没有做到“多实例同时运行”。Nacos 只解决配置集中管理和动态刷新，不能替代执行权、租约、fencing token、可靠输入队列和数据库并发控制。直接启动两个实例会产生重复执行、旧结果覆盖、限流失真和启动恢复误伤。

## 1. 总体判断

| 能力 | 当前状态 | 集群要求 |
|---|---|---|
| HTTP 受理 | 任意实例都可受理 | 可以，但执行权必须由分布式锁决定 |
| 任务持久化 | 运行库已改为共享 PostgreSQL；本地回归测试使用 H2 | 共享数据库中的结构化列、索引、版本条件更新 |
| 单进程恢复 | 有，按 `generation` 防止旧订阅提交 | 需要跨节点租约、心跳、fencing token |
| 执行归属 | 本机 `TaskService.owned` 内存映射 | Redis 锁或数据库租约，不能靠本机映射 |
| 输入与取消通知 | 写数据库，执行节点轮询检查 | Redis Stream 可靠投递 + Pub/Sub 唤醒 |
| 并发与限流 | 本机计数和数据库窗口读改写 | 全局限流、原子额度、跨节点一致 |
| 后台扫描 | 每个实例都会扫描全部任务 | 单例扫描或带租约的任务领取 |
| 副作用恢复 | 启动时把所有 `RUNNING` 改成 `UNKNOWN` | 只处理租约过期的记录，不能误伤其他节点正在执行的操作 |
| 配置 | 本地 `application.yml` 和环境变量，启动时绑定 | Nacos 集中配置、命名空间隔离、刷新策略 |
| 部署 | 没有容器、健康检查、优雅停机 | 容器、探针、滚动发布、优雅摘流 |

## 2. 已经具备的基础

这些能力可以保留，不需要重写：

- 任务、检查点、会话历史、偏好、审批、副作用账本、提示词和目录都已经落在数据库，不依赖进程内存作为唯一事实。
- 任务提交是异步执行，HTTP 等待者取消不会取消已经受理的任务，见 `TaskService.submit`。
- 任务有绝对截止时间、共享模型预算、检查点恢复和 `generation` 写回校验。
- 业务幂等键已经覆盖请求、指令、委派、工具调用和外部副作用。
- 运行详情、配置快照、指标、审批和目录都通过数据库读取，适合多实例共享。
- 前端静态资源打包在服务内，不依赖本机文件。

这些基础说明改造重点不是“把状态搬到 Redis”，而是把本机归属判断和后台扫描改成跨节点可协调。

## 3. 关键缺口

### 3.1 Nacos 配置中心还没有接入

现状：

- `pom.xml` 没有 Nacos 或 Spring Cloud Alibaba 依赖。
- `src/main/resources/application.yml` 只有本地配置，没有命名空间、分组、配置版本和刷新策略。
- `SupervisorSettings`、`SupervisorPolicySettings` 是启动时绑定的不可变记录；`TaskService` 和 `TaskStoreService` 在构造器中长期持有这些对象。
- `GET /config` 只能证明当前进程启动时的值，不能证明配置来自 Nacos，也不能证明配置变更已经生效。

需要补齐：

1. 引入 Spring Cloud Alibaba Nacos Config，使用 `cluster` 配置档案启用，单机默认档案不强制连接 Nacos。
2. 明确 `namespace`、`group`、`dataId` 约定，例如 `supervisor-${spring.profiles.active}.yaml`。
3. 建立配置变更后的刷新边界：新任务读取新策略，在途任务保留受理时的策略快照，避免同一任务前后行为漂移。
4. 配置中心的用户名、密码、模型密钥和认证令牌不能明文写入仓库；使用环境变量、Kubernetes Secret 或配置中心加密能力。
5. `/config` 增加配置来源、配置版本或最后刷新时间，便于验收。

### 3.2 数据库已改为 PostgreSQL，迁移脚本尚未独立

已落地（2026-11-02）：

- 运行库默认连接 `jdbc:postgresql://127.0.0.1:5432/supervisor`，地址、账号、密码和连接池由 `SUPERVISOR_DATABASE_*` 环境变量提供。
- `Database` 通过 `DatabaseIdProvider` 区分数据库；H2 专用的 `SET WRITE_DELAY 0` 只在 H2 连接上执行。
- Mapper 已按方言拆分：`MERGE INTO ... KEY(...)` 保留给 H2 回归测试，PostgreSQL 使用 `INSERT ... ON CONFLICT ... DO UPDATE`。
- 大文本改用 `TEXT`，自增主键改用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`，浮点改用 `DOUBLE PRECISION`。
- 已在临时 PostgreSQL 17 实例上验证启动建表、任务创建与读取、偏好写入与更新、提示词登记；全量 362 项回归测试在 H2 上通过。

仍需补齐：

1. 用 Flyway 或 Liquibase 接管表结构，当前建表仍依赖启动时 `CREATE TABLE IF NOT EXISTS`。
2. 集群验收必须跑 PostgreSQL，H2 只用于单机回归测试。

集群后果（改造前）：多个实例无法共享同一个本地 H2 文件，且换成 PostgreSQL 后原 SQL 不能直接运行。该后果已随上述改造消除。

### 3.3 任务表缺少集群所需的结构化字段和索引

现状：

- `supervisor_tasks` 只有 `run_id`、租户、用户、会话、请求编号、创建时间和 `payload`，见 `TaskMapper.xml:7-12`。
- `state`、`deadline`、`generation`、父运行、根运行都在 JSON `payload` 内。
- 恢复扫描每次读取全部任务并反序列化，见 `TaskRepository.all()` 和 `TaskService.recover()`。

集群后果：

- 无法按状态和截止时间建立索引，任务量上来后每个实例每秒扫描全表。
- 无法用数据库条件更新直接判断执行权和状态迁移。
- 无法在数据库层保证同一会话只有一个活动任务。

需要补齐：

- 增加 `state`、`deadline_at`、`version`、`execution_epoch`、`last_owner`、`heartbeat_at`、`parent_run_id`、`root_run_id`、`updated_at` 等列。
- 增加 `(state, deadline_at)` 扫描索引和 `(tenant_id, user_id, session_id)` 活动任务唯一约束。
- 兼容期保留 `payload`，但执行权和状态判断逐步改为结构化列加条件更新。

### 3.4 本机 `synchronized` 不能保护多实例

现状：

- `TaskStoreService` 的创建、指令、提交、预算预留、检查点等方法都使用 `synchronized`，见 `TaskStoreService.java:61-115`、`TaskStoreService.java:464-490`。
- `TaskRepository.save` 每次把完整 `payload` 覆盖写入。
- `TaskRepository.reserve` 先读分钟窗口，再计算，再覆盖写，见 `TaskRepository.java:100-121`。

集群后果：两个实例同时读取同一任务或同一分钟窗口，后写入的请求会覆盖先写入的结果；`synchronized` 只在本进程内有效。任务预算、检查点、指令状态都可能丢更新。

需要补齐：

1. 任务写入使用 `version` 或 `execution_epoch` 做条件更新，影响行数为 0 时重读并拒绝旧写入。
2. 分钟窗口额度使用数据库原子更新、行锁或 Redis 原子计数，不能读改写覆盖。
3. 同会话活动任务用数据库唯一约束或会话级分布式锁保证，不能只靠先查后插。

### 3.5 执行权仍由本机映射决定

现状：

- `TaskService.owned` 是 `HashMap`，只表示本实例正在跑哪些任务，见 `TaskService.java:52-53`。
- `create`、`applyInstruction`、`recover` 都通过 `owned.containsKey` 判断是否启动，见 `TaskService.java:217-223`、`TaskService.java:348-370`。
- `TaskStoreService.claimExecution` 只把 `generation` 加一，没有数据库 `execution_epoch` 条件更新，见 `TaskStoreService.java:863-873`。

集群后果：两个实例都会认为任务不属于自己，都会调用 `claimExecution` 并启动执行；最后一次覆盖 `payload` 的实例获胜，另一个实例仍可能在跑模型、调工具和写结果。

需要补齐：

1. 增加节点编号，例如实例 UUID 加启动批次。
2. 执行前抢 Redis 锁 `lock:run:{runId}`，锁值包含节点编号和随机 nonce。
3. 抢到锁后从数据库申请递增的 `execution_epoch`，作为 fencing token。
4. 所有写回带 `execution_epoch` 条件；旧执行者写回影响行数为 0 时必须立即停止。
5. 续租失败时取消本实例执行，不再调用模型和外部写工具。

这一项是集群运行的 P0 前置条件，不能只用 Nacos 或数据库乐观锁替代。

### 3.6 没有可靠输入队列和跨节点唤醒

现状：

- 指令和子 Agent 消息写入数据库队列，执行节点在模型或工具边界主动读取。
- 注释明确说客户端断开不会取消任务，但对跨节点“有新输入”的即时唤醒没有实现。
- 取消、切换、子 Agent 中断依赖执行节点自己检查状态，见 `TaskService.applyInstruction` 和 `interruptAgentWithReceipt`。

集群后果：请求落到节点 A，任务在节点 B 执行时，A 只能写数据库，B 不能立即被叫醒；取消和切换的响应时间取决于 B 下一次轮询或模型调用边界。

需要补齐：

- Redis Stream 保存用户输入、取消指令和完成事件，消费组按 `runId` 消费，处理完 `XACK`，节点挂掉后用 `XAUTOCLAIM` 接管。
- Redis Pub/Sub 只负责“有新输入或任务完成”的唤醒，消息丢失不影响正确性。
- 所有输入按 `instructionId` 去重，消费者不能因为重放执行两次。

### 3.7 每个实例都跑全量恢复和清理扫描

现状：

- `TaskService` 每个实例启动独立恢复线程，每秒调用 `recover()`，见 `TaskService.java:99-115`、`TaskService.java:348-375`。
- `recover()` 扫描全部任务、过期任务、子任务、未投递通知、任务保留期和会话保留期。
- `SideEffectReconciler` 每个实例都启动一个线程，每秒核对同一批副作用记录，见 `service/SideEffectReconciler.java:20-55`。

集群后果：同一任务被多个实例重复扫描和启动；清理任务、通知重试和副作用核对重复执行；数据库负载随副本数线性增加。

需要补齐：

1. 恢复扫描使用数据库租约或 Redis 锁领取任务，抢到才接管。
2. 清理、通知重试、副作用核对使用单例调度或 `FOR UPDATE SKIP LOCKED` 领取批次。
3. 每次扫描只读取待处理索引范围，不能全表反序列化。

### 3.8 副作用账本启动恢复会误伤其他节点

现状：

- `SideEffectRepository` 构造时执行 `markRunningUnknown()`，把所有 `RUNNING` 记录改成 `UNKNOWN`，见 `repo/SideEffectRepository.java:18-24`。

集群后果：节点 B 正在调用下游执行写操作时，节点 A 重启会把 B 的记录改成 `UNKNOWN`，造成状态误判和不必要的下游核对。

需要补齐：

- 副作用记录增加 `owner`、`lease_until`、`heartbeat_at`。
- 启动时只恢复租约过期或执行节点已失效的记录。
- 状态迁移使用条件更新，旧 owner 不能覆盖新 owner。

### 3.9 并发和限流只在本机生效

现状：

- `hasCapacity` 统计本机 `owned`，见 `TaskService.java:812-827`。
- 全局并发、每用户并发、子 Agent 并发上限都是本机视角。
- 分钟窗口额度虽然有数据库表，但读改写不是原子操作，见 `TaskRepository.java:100-121`。

集群后果：配置“全局最多 8 个并发”时，两个实例可能各跑 8 个；429 是否出现取决于请求落到哪个节点。

需要补齐：

- 全局并发和每用户并发使用 Redis 计数或数据库原子计数。
- 分钟窗口使用原子 `UPDATE ... RETURNING`、行锁或 Redis Lua。
- 子 Agent 活动数量也要跨节点计算，不能只看本机 `owned`。

### 3.10 注册表和提示词种子存在启动竞争

现状：

- `AgentCatalogService` 和 `PromptRegistryService` 构造时检查表是否为空并写入种子，见 `service/AgentCatalogService.java` 构造器和 `service/PromptRegistryService.java:seed()`。
- 多实例同时启动时可能同时判断为空，然后同时插入。

集群后果：唯一键冲突可能导致某个实例启动失败；审计表也可能重复写入启动验签记录。

需要补齐：

- 种子写入使用幂等插入或 `ON CONFLICT DO NOTHING`。
- 启动验签和审计写入按节点编号记录，允许重复但可区分。
- 注册表变更是否需要跨节点缓存失效，单独设计。

### 3.11 部署和运行支撑缺失

现状：

- 仓库没有 Dockerfile、Kubernetes 清单、健康检查、就绪检查和优雅停机配置。
- 只有 `application.yml` 中的 `server.address` 和 `server.port`。
- 没有 PostgreSQL、Redis、Nacos 的本地或集群编排文件。

需要补齐：

- 容器镜像、非 root 用户、只读根文件系统、资源限制。
- `/actuator/health` 或等价的存活/就绪接口，数据库和 Redis 不可用时要能正确反映。
- `server.shutdown=graceful`、停止接收新请求、停止续租、写完检查点后退出。
- Kubernetes Deployment、Service、Ingress、PodDisruptionBudget、反亲和和滚动发布策略。
- PostgreSQL、Redis、Nacos 的高可用、备份、网络策略和凭据管理。

### 3.12 缺少集群级测试和故障演练

现状：现有测试都是单实例或单进程恢复测试，没有两个实例同时操作同一任务、Redis 故障、Nacos 不可用、锁过期后旧节点恢复等场景。

需要补齐：

- 两实例集成测试：同一 `runId` 只有一个执行者。
- 杀实例测试：锁过期后接管，旧实例写回被 fencing token 拒绝。
- Redis 主从切换测试：允许短暂重复，但不能产生两次外部写。
- Nacos 断连和配置回滚测试：实例启动失败要明确，不能静默使用旧值。
- 数据库连接中断和事务回滚测试。

## 4. Nacos 接入建议

### 4.1 依赖和配置档案

建议使用 Spring Cloud Alibaba 2023.0.3.4 作为候选版本，与当前 Spring Boot 3.3.5 做一次依赖兼容性验证后再固定版本。不要直接引入 2025 版本而不升级 Spring Boot。

单机默认档案保持本地配置；新增 `cluster` 档案，只有集群部署时启用 Nacos。示例配置结构：

```yaml
spring:
  config:
    activate:
      on-profile: cluster
    import: nacos:supervisor-cluster.yaml?group=SUPERVISOR&refreshEnabled=true
  cloud:
    nacos:
      config:
        server-addr: ${NACOS_SERVER_ADDR}
        namespace: ${NACOS_NAMESPACE}
        group: ${NACOS_GROUP:SUPERVISOR}
        username: ${NACOS_USERNAME}
        password: ${NACOS_PASSWORD}
```

启动参数或环境变量提供 Nacos 地址、命名空间和凭据。集群档案下 Nacos 不可用时应明确启动失败，不能静默回退到本地默认值。

### 4.2 动态刷新边界

配置刷新不能直接改变正在执行的任务。建议：

- 任务受理时固定一份策略快照，写入任务检查点。
- 新任务读取最新 `SupervisorPolicy` 和 `SupervisorSettings`。
- 在途任务继续使用受理时的快照，避免同一任务前后行为不一致。
- 配置刷新只影响新任务和后台扫描参数，不改变已经发出的模型请求。

当前 `TaskService` 和 `TaskStoreService` 在构造器中长期持有配置对象，需要改成“每次受理读取当前快照”，或者引入一个可替换的运行时配置提供者。不能只加 `@RefreshScope`，否则可能重建服务对象并影响正在运行的任务。

### 4.3 配置内容边界

放入 Nacos 的内容：

- 策略开关、阈值、限额、下游地址、超时、日志级别。
- 提示词和 Agent 目录的版本指针可以使用 Nacos，但正文仍由数据库注册表管理，避免两套事实来源。

不放入 Nacos 明文的内容：

- 模型供应商密钥、认证令牌、数据库密码、下游凭据。
- 这些值通过 Kubernetes Secret、环境变量或配置中心加密能力注入，并在 `/config` 中只显示“已配置”，不返回值。

### 4.4 Nacos 不负责的事情

Nacos 配置中心不能替代：

- Redis 任务锁、续租、fencing token。
- Redis Stream 的可靠输入队列。
- 数据库的状态、检查点、预算和幂等。
- 全局并发控制和限流。

所以“接入 Nacos”只是集群改造的一项，不是全部。

## 5. 推荐实施顺序

### P0：先保证多实例不会重复执行和互相覆盖

1. PostgreSQL 迁移和 Flyway。
2. 任务表结构化字段、索引和版本条件更新。
3. 节点编号、Redis 锁、租约续期、fencing token。
4. 副作用账本按租约恢复，去掉启动时全量改成 `UNKNOWN`。
5. 恢复扫描按锁领取任务，避免全量扫描。

验收：两个实例同时收到同一会话请求，只有一个创建任务；杀掉执行实例后另一个接管；旧实例写回被拒绝；外部写操作只执行一次。

### P1：补齐集群运行能力

1. 接入 Nacos，完成命名空间、配置分组、刷新边界和凭据注入。
2. Redis Stream 输入队列和 Pub/Sub 唤醒。
3. 全局并发、每用户并发和分钟额度原子化。
4. 注册表种子幂等和后台任务单例化。
5. 健康检查、优雅停机、容器和 Kubernetes 清单。

验收：滚动发布期间没有任务丢失；配置修改只影响新任务；节点扩容后全局限流仍然准确。

### P2：补齐可观测和故障演练

1. 锁等待、续租失败、fencing 拒绝、接管次数、配置刷新失败等指标。
2. 两实例、Redis 故障、Nacos 故障、数据库故障的自动化演练。
3. 日志关联 `runId`、`nodeId`、`executionEpoch` 和 `traceId`。

## 6. 文档冲突需要先定

`docs/集群环境部署改造方案.md` 主张 Redis 负责锁和输入队列；`docs/技术方案.md` 当前写的是“不采用 Redis，使用 PostgreSQL 租约和 outbox”。两套方案不能同时作为实施依据。

建议定案：

- PostgreSQL 保存任务、运行、检查点、预算、审批和副作用的最终事实。
- Redis 只保存执行锁、租约、输入 Stream 和唤醒通知，不作为关键事实的唯一副本。
- fencing token 来自数据库 `execution_epoch`，不能来自 Redis 自增。
- 同步修改 `docs/技术方案.md` 中“不采用 Redis”的表述，避免后续实现各按一套文档。

## 7. 最小集群验收清单

在宣称“可以在集群运行”之前，至少完成：

- 两个应用实例共享 PostgreSQL 和 Redis。
- 同一 `runId` 同时只有一个执行者。
- 杀掉执行实例后，另一个实例在锁过期后接管。
- 旧实例恢复后写回被 `execution_epoch` 拒绝。
- 同一 `requestId` 和同一 `instructionId` 跨实例重放只生效一次。
- 外部写操作只执行一次，结果不明只查询不重放。
- 全局并发和分钟额度在实例扩容后仍然准确。
- Nacos 不可用时集群实例明确启动失败或保持最后已知配置，不静默切换成本地默认值。
- 滚动发布期间没有任务丢失，也没有重复外部写。
- PostgreSQL、Redis、Nacos 都有备份、恢复和故障演练记录。
