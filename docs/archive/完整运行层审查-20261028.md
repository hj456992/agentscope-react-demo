## 仍需修复并验证

### P1：模型请求网络异常在 SDK 包装层被错误判成不可重试

位置：`src/main/java/dev/garden/demo/supervisor/ToolExecutor.java:113-114`。

当前 `if (error instanceof ModelHttpException http) return http.isRetryableHttpStatus()` 在状态码为空时也立即返回 false。已核对本地 AgentScope 2.0.1 sources `io/agentscope/extensions/model/openai/OpenAIClient.java:719-720`：HttpTransportException 被包装成 `new OpenAIException(message,cause)`，该外层实现 ModelHttpException，但 statusCode 为 null。因此真实连接失败/SocketTimeout cause 永远无法继续匹配下面的可重试分支。不是理论异常；这是 SDK 正常网络失败路径。

建议仅已知 statusCode 时作 HTTP 分类，缺失状态继续沿 cause；增加真实 OpenAIException→HttpTransportException→ConnectException/SocketTimeoutException 用例，仍要求每次实际发送扣共享额度。

### P2：标准 429 insufficient_quota 响应仍会耗预算盲重试

位置：`ModelHttpTransport.java:40-42`、`ToolExecutor.java:109-114`。

传输看到 body 包含 insufficient_quota 时将响应交给 SDK，而非建立明确不可重试结果。AgentScope OpenAIClient 的非2xx处理 `:309` 使用 `OpenAIException.create(statusCode,errorMessage,null,responseBody)`，实际 errorCode=null。后续只检查 provider.getErrorCode() 无法识别配额耗尽，429 会被当暂时限流重试。建议传输层读取结构化 error.code 并抛明确不可重试异常，或统一分类时检查 SDK 已保留的响应体；不能用任意子串误判正常内容。用标准非2xx JSON 而非直接构造带 errorCode 的测试验证。

### P2：未知写入核对可被缺少适配器的记录永久饿死

位置：`SideEffectLedger.java:116-126 reconcile`。

SQL 先从全部 UNKNOWN 中 ORDER BY next_lookup LIMIT batchLimit，再跳过 map 中没有 adapter 的记录。前20条都来自已移除适配器时，其 next_lookup/lookup_count 永不改变，后续已配置工具的UNKNOWN每次都排在LIMIT之外，永远无法核对。此问题在服务重启变更adapter配置后可触发，不要求新增业务写入接口。

建议查询按已注册工具过滤，或分页寻找实际可核对记录直到批量预算用完；保留未配置记录。测试至少21条，前20条无adapter，第21条adapter可查询，必须实际处理第21条。

### P2：SWITCH 新建任务绕过 maxStoredTasks

位置：`TaskService.java create:150` 与 `applyInstruction` 的 SWITCH 分支（约270起）。

普通 chat 创建会检查持久任务总数；SWITCH 直接 newTask/save(next)，没有相同检查。配置 maxStoredTasks=1 时首个RUNNING任务仍可切换生成第二行，违反已提供的容量上限。应在同事务检查，容量不足返回429且旧任务保持活动，不扣新任务速率、不产生部分替换记录。

## 本轮发现、已看到修复但待主任务定向测试

### P1：跨 JVM 的逻辑步骤 hash 不稳定

初始位置 `RunContext.fingerprint`（原约288）；model、normalized、child等多处 Map.of。

之前去除 Msg.id/timestamp 修复了同进程重建，但 fingerprint 仍直接 Jackson 序列化 Map.of。JDK 不可变map迭代顺序跨JVM可变化，导致相同JSON对象得到不同SHA-256。已真实启动多个独立JShell，在相同classpath上运行 `JsonUtils.getJsonCodec().toJson(Map.of("decision","X","sourceVersion","Y"))`，得到两种输出：

- `{"sourceVersion":"Y","decision":"X"}`
- `{"decision":"X","sourceVersion":"Y"}`

这会同时破坏恢复时的步骤次数限制和子任务缓存命中。已看到主任务新增 `canonicalJson/canonicalNode` 递归排序对象键、保留数组顺序，fingerprint 改为使用该规范化结果。静态审查修复方向正确；需要独立进程同hash测试及持久恢复预算测试，不能只比较同一JVM里的Map构造顺序。

### P2：多个合法追加合并后超过单条问题上限

位置：`TaskService.drainInput:571`，`Supervisor.execute:69`。

原实现允许32个各≤2000字符消息，drainInput 直接join并清pending/推进consumedRevision；Supervisor随后把合并结果当新question重新限制2000字符。两条各1200字符已受理输入会被FAILED而非执行。已看到新的受理前 pendingCharacters 检查（约295-299），在事务修改前拒绝超过合计2000；静态方向正确。验收需断言被拒绝的第二条不改变revision、pending、userInputs和instruction replay记录，第一条仍正常消费。

### TaskRepository 强制同步刷盘

已读到构造器 `TaskRepository.java:42 SET WRITE_DELAY 0`，与SideEffectLedger保持一致。这个修复应由真实子进程崩溃测试验证，正常close/reopen不能证明进程突然停止后的提交持久性。

## 运行层审查要点

- 受理、显式指令、结束提交均经过短repository事务；任务与当前会话号有独立持久fence，避免仅靠createdAt排序。同revision/generation检查防止旧结果覆盖新输入和取消。HTTP等待只读view轮询，任务订阅由TaskService持有。
- SUPPLEMENT/REVISE排队不立刻取消正在进行的模型；停止/切换改变generation并dispose。结束前revision不一致再次cycle，避免最后一次boundary后来的输入丢失。仍需上述合计输入边界测试。
- 预算持久预留把步骤尝试、任务调用、全局分钟调用/token放在同事务，失败回滚；task deadline绝对时间恢复不刷新。H2本地单进程，不是多节点租约。
- TaskService.view在返回已完成结果或请求号回放前逐证据核对权限；PersistentControl每次resolve当前映射；身份移除取消恢复。实际权限外部动态管理不在此服务提供范围内。
- ConversationService独立保存明确偏好、源消息和助手回答权限要求；用户记录不复制注入后的history，避免显式偏好删除后从应用生成摘要自动重新装入。记忆版本墓碑和失效清理存在。
- SideEffectLedger的稳定下游操作键包含租户/用户/工具/操作，递归canonical参数、先RUNNING持久记录后submit，UNKNOWN只lookup，确认未执行且下游幂等才有限重试，定时器不submit。任务取消与账本核对分离，外部效果不能靠本地取消回滚。单实例与下游权威查询假设已清楚声明。
- 实际工具执行池是固定8线程/32队列，忽略中断仍占原物理线程；不能把任务订阅取消等同远端计算已停止。运行层容量和I/O物理容量含义应分别记录。
