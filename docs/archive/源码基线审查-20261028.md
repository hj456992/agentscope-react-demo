## 重要基线问题

1. **P1：真实模型答错可以在成功证据存在时直接返回 SUCCESS。** `J:Supervisor.java:72-81 finish` 只检查 evidence 状态及答案非空，然后原样拼接模型的 answer。`J:RunContext.java:52-63 outcome` 不比较答案字段与证据。触发：工具返回杭州 18℃，模型写 99℃，仍可 SUCCESS。提示词「不得编造」不是程序保证。若用户要求正确证据不得变成错误答案，需要明确的业务答案校验/证据渲染扩展；不能称它已经存在于 Codex 工具分发源码。
2. **P1：取消/超时释放的是请求名额，不能保证底层同步数据源已结束。** `J:RequestGate.java:18-23` 由 Mono.using 在取消时释放；`J:Supervisor.java:62` 超时取消订阅；`J:TravelTools.java:54-60,77-83` 同步调用 DataSource，没有专门执行许可或取消感知。故阻塞或忽略中断的数据源可能仍运行而新请求已被准入。已有 `timeoutCancelsPendingChildModel` 只证明 Flux 取消通知，不证明 I/O/副作用停止。需要额外覆盖挂起的数据源和实际占用计数。
3. **P1（需求差距）：请求不是可继续的会话运行实例。** `J:Supervisor.java:31-41` 每次订阅新 RunContext/Agent；`J:SupervisorContracts.java:18-21` history 完全来自客户端；`J:SupervisorController.java:22-32` 仅一个 chat 接口。相同 sessionId 可并行运行、各有新预算；没有活动轮次队列、turnId 校验、追加、替换或显式停止。不能把普通后续 HTTP 请求说成 Codex steering。
4. **P1（需求差距）：六轮字符裁剪不是上下文预算或压缩。** `J:QueryRewriter.java:37-47` 反向选最多六轮/6000 字，遇到单个过长轮次即 break；更早约束直接消失。`J:RunContext.java:36-45` 只检查调用次数和 deadline，未计算系统提示、工具 schema、当前输入、工具输出、摘要、预留输出等完整输入。`J:TravelTools.java:92-96` 保存并返回任意大小数据，事件又包含相同 JSON。需要明确的完整请求大小控制和可追溯压缩，不应仅换一个截取常量。
5. **P2：失败尝试永久污染最终状态。** `J:RunContext.java:52-59` 对所有历史 evidence 求 anyMatch(FAILED/INVALID_INPUT)，`childFailed` 也从不复位。模型第一次错参数、收到反馈后成功，最终仍 PARTIAL；应区分尝试日志与当前逻辑步骤最终结果，保留错误诊断但不把恢复成功当最终失败。
6. **P2：错误类别在边界被抹平。** `J:TravelTools.java:58-60,81-83` 将所有数据源异常折叠 FAILED；`J:ChildAgentDispatcher.java:60-69` 将 ERROR/DENIED/INTERRUPTED/所有异常折叠同一子失败；`J:Supervisor.java:63-67` 只区别外层 TimeoutException，其余预算、参数、权限、模型故障均 FAILED。无法据此实现分类重试、预算终态或明确取消；但不应反过来对整个 Supervisor 重试。
7. **P2（需求差距）：去重、持久化、权限均不存在应用级实现。** `J:ChildAgentDispatcher.java:41,51-56` 每次新子 Agent；`J:TravelTools.java:42,64` 每次有效参数直接调用数据源；`J:RunContext.java:19-22` 全内存，`sessionId` 非认证身份。角色只暴露工具确实存在于 `J:TravelAgentFactory.java:27-55`，但不能证明租户/用户/资源权限、幂等、重启恢复或缓存回放权限。
8. **P2：业务参数校验的可信依据仍来自模型自己。** `J:IntentRecognizer.java:24-33` 获取模型 Decision，`J:TravelTools.java:47-49,70-72` 只对比 Decision，不能证明 Decision 与用户原文中的否定、日期、城市约束一致。`clarification:36-48` 只做缺失、同城、日期格式、天数下界；不要将这些写成完整语义验证。

## 6. 重试分类及副作用边界

- `C:codex-rs/protocol/src/error.rs:418 CodexErr.retry_delay` 显式枚举：TurnAborted、SessionBudgetExceeded、Interrupted、InvalidRequest、InvalidPrompt、ModelNotFound、QuotaExceeded、UsageLimitReached、ContextWindowExceeded 等不重试；网络/stream/timeout/部分 server/rate-limit 等使用 server delay 或 backoff；ServerOverloaded/RetryLimit 需要服务器 delay。
- `C:codex-rs/core/src/responses_retry.rs:60 handle_response_stream_error` 先取 retry_delay；terminal 直接返回；有限请求重试遵守 max_retries/Retry-After；网络可在显式 UnboundedConnectionRetries feature 下走特殊分支；到上限可能切换传输并重置重试数，但先等待 server deadline。不能删去这些适用条件后称「上游所有错误最多 3 次」或「上游绝不无界重连」。
- 上述为 **Responses 请求/stream 重试**，不是任意业务工具重试保证；本地 compact 还存在单独 retry 分支。Java 需分别控制模型请求、读工具、写工具，不能给整个三阶段链套 retry 导致成功步骤重复。
- 当前 `.modelExecutionConfig(maxAttempts(1))` 与 `.maxRetries(1)` (`J:TravelAgentFactory.java:63-64`) 显示应用试图限制 SDK 重试，但未审核 AgentScope 依赖全链条，不从这些 builder 参数推定底层 HTTP 永无重试。
- 业务幂等键、写入超时查状态、下游效果与本地事务原子性、跨重启永久防重、任意任务 DAG 自动恢复、RAG 语义真实性验证：本次所查 Codex/Claude 调用链 **没有证明这些通用保证**。不是断言整个仓库绝无相关特例；它们必须保留用户要求并列成具体业务扩展，不允许拿 callId、history resume 或工具 isError 代替。

## 建议的行为验收，不作为新增范围决定

1. 追加输入保持同一 turn ID、排队消费，expectedTurnId 错误不影响当前轮次；与显式 replace/interrupt 分开验证。
2. 取消未完成 spawn 清理临时 child；accepted child 与父轮次取消边界明确；树关闭单独验证。
3. 经真实 SDK 工具调用链测试未知工具、缺字段/错类型、handler 异常与 Fatal，并断言下一次模型确实看见失败输出。
4. 验证「先错误后成功」最终成功，错误尝试仍可审计；独立工具失败不覆盖其他成功结果。
5. 完整模型输入超长、工具返回超长、最早确认条件、压缩失败/中断、工具 request/output 配对；不能只验证 6 轮截取。
6. 对所有错误分类做模型请求重试测试；验证重试一次只重试失败步骤；服务 Retry-After 不绕过截止时间。
7. 数据源忽略取消仍运行时不得超发执行许可；写入结果未知不能声称被取消撤回。
8. 会话 resume 仅还原已经持久化内容；业务自动恢复、幂等和答案校验另有明确需求/实现/测试，不能借上游名义兜底。

此报告的结论来自静态调用链与既有测试检查，未执行或编写项目业务代码，未运行新测试，不将建议用例标为已通过。
