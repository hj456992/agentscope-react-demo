## 实施变化与可靠性复核

运行控制新增角色、路径、稳定逻辑回合、spawn/send/followup/interrupt/list/wait/mailbox 接口。CLI 使用独立本地控制；持久服务继续由 TaskService 调度、TaskStoreService 声明式事务、MyBatis 仓储处理。未新增生产构造器重载、JDBC 或编程式事务，未移动用户已审阅的分层。

- 子会话拥有独立任务、执行代际、检查点与取消状态。模型预算仍由树根累计，但读取预算不要求根仍 RUNNING。HTTP 根准入保留原配置；子活动上限单独采用 `AgentLifecycle.MAX_ACTIVE_CHILDREN=8`，不计根。8 是当前本地资源配置，不是 Codex 默认值。
- `TaskStoreService:566-631` 协作回执以稳定 `agentTurnId + call_id` 定位，附参数指纹；执行恢复只提升 generation。spawn 接受、send/followup 入队、interrupt 状态变更分别与回执同事务。接受提交后、子启动或模型历史保存前崩溃，恢复从已接受记录继续；重放相同 call 返回原回执，异参拒绝。
- `TaskService:459-530` 在执行与重放入口解析当前身份；interrupt 的旧结果、list 和 mailbox 结果重新检查证据工具权限。spawn 回执保存的是接受时无结果快照；send 回执对外不返回结果，未发现通过回执读取被撤权证据的路径。
- `TaskStoreService:723-784` 输入与邮箱先移入持久 inflight 批次，只有 `loop:v3.3` 保存和匹配 delivery token 的确认同事务成功才删除批次。新控制器确认 token 初始为零，构造阶段保存旧快照不会误确认旧进程读过的消息。Supervisor 已改为整批邮箱入历史后保存一次，避免第一条保存提前确认整个批次。
- mailbox 使用独立序号，不递增公共用户输入 revision。用户输入逐条保留边界；NEEDS_INPUT 回答与原 call ID 配对由循环处理，存储层不把通知伪装成用户回答。
- 取消后的同 HTTP session 新 chat 仅继承前一 CANCELLED 根的 `loop:v3.3` 及明确中断/新输入标记，不复制整个执行缓存。上下文层以逻辑回合幂等补 aborted、追加真实用户输入并清标记。

取消续接仍保留现有 HTTP 新 runId、期限和预算约定；旧已接受子仍属于旧 rootRunId/parentRunId，通知旧直接父。新 HTTP run 并未接管旧树身份，不能把上下文续接表述为完整 Codex 同 ThreadId 会话迁移。

## 冻结复核发现及修正

**P1：父邮箱满时延迟的完成通知会被后续 followup 覆盖。** 原实现以 `child.result` 暂存欠投通知，followup 开启下一轮会清空它。两条新增回归已由主代理串行执行为红：持久版预期 `[first result, second result]`、实际 `[second result]`；本地版也只收到第二轮，记录为 `/tmp/v34-outbox-red.log`（2 failures、0 errors）。

经主代理指示继续修复：TaskDO 与本地节点增加独立 `completionOutbox`，每条包含完成代际与完整消息。`completionQueuedGeneration` 保证每代入队一次，原 `notifiedGeneration` 继续表示实际投递的代际；结果落盘和入队同事务，向父邮箱投递和移出队列同事务。父邮箱满则保留有序队列；followup 只清本轮 result，不清旧通知。恢复扫描也处理已经进入下一轮 RUNNING 的子会话。没有改为拒绝 followup。

新增 `pendingCompletionsSurviveFollowupAndPersistentReload` 与 `localPendingCompletionsSurviveFollowup` 覆盖满邮箱、两轮完成、恢复/腾空后按序且各一次投递。主代理随后执行 `/tmp/v34-full-second.log`：AgentLifecycleTest 15 项中仅新补的容量回归失败，原 12 项与 outbox 两项均通过。

独立复核另指出 P2：本地 followup 唤醒闲置子时没有复用 spawn 的活动容量约束。新增 `localFollowupRejectsFullChildCapacityBeforeEnqueue` 在上述 full-second 中观察到“应抛 BudgetExceeded、实际未抛”的红结果。随后在目标邮箱写入和 generation 增加之前添加同树活动子上限检查；被拒绝时不入队、不改变目标 completed 状态。运行中投递及 QueueOnly 不占新槽。该最后修正待串行复测。

另外三条必要边界已按真实失败证据修正，红记录为 `/tmp/v34-last-boundaries-red.log`（4 tests、4 failures、0 errors）：

- **P1：多层通知扫描覆盖邮箱。** 扫描初始聚合快照中，前一后代向父投递后，后一旧父快照可能再次覆盖邮箱，尤其 created_at 同毫秒或时钟回拨时。重投现在只用扫描结果枚举标识，每项实际操作前重读最新聚合；`outboxScanPreservesMailboxWrittenByEarlierDescendant` 用逆序时间戳验证不依赖扫描顺序。
- **P1：历史内容缺少本轮新 evidence 时权限来源丢失。** `AgentMessageDTO`、`AgentSnapshotDTO` 增加不可变 requiredPermissions 集合；从 loop 历史清单、继承清单及当前 evidence 合并，普通转述消息与完成通知均携带。服务在 mailbox/list/interrupt 回执回放前按当前身份重新校验。本地控制同样传递、读取时校验。`completionCarriesHistoricalPermissionsWithoutCurrentEvidence` 验证无本轮 evidence 的结果仍保留旧天气权限；HTTP view 与 requestId 重放补充 `completedHttpViewAndIdempotentReplayCheckHistoricalPermissions`，在 `/tmp/v34-history-view-red.log` 观察到应拒绝却返回结果后，将 view 统一改为历史与 evidence 权限并集检查，拒绝返回 403。
- **P1：共享次数额度用尽后父等待拖到超时。** 源码 `agent/control/budget.rs:12-16` 与 `rollout_budget.rs:48-70` 只证明共享响应 usage 累计与 SessionBudgetExceeded，没有证明会取消整树或唤醒 wait。本项目次数预留是 Java 额度适配：邮箱/输入为空、共享调用次数已满、当前子树无 RUNNING 后代时，wait 立即返回 BudgetExceeded；有活动后代仍等其输出。嵌套等待从叶到祖先释放，普通 interrupt 不生成完成通知。本地预算异常改为 BUDGET_EXHAUSTED，而非误写 FAILED。两条 wait 回归覆盖持久与本地控制。

## 最后权限链补充

最终复核发现，仅保存本轮 evidence 会使服务端连续会话丢失来源：A 查询资料，B 引用 A 而不产生新证据，撤权后 C 仍可能读取 B。新增两条回归在 `/tmp/v34-history-chain-red.log` 明确失败后修复：

- `ConversationService.enrichWithPermissions` 单次读取并返回装配请求与实际展示内容的权限；只统计最近六条可见助手回答。隐藏回答和仅保留用户问题的旧摘要不附加已移除资料权限。`ConversationContextDTO` 是内部跨层对象，不改变用户 RequestDTO。
- `TaskStoreService.newTask` 将该权限写入 `agent:inherited-permissions`，由 fresh LoopConversation 初始化读取；取消续接已有 loop 时仍使用快照自己的历史权限。
- 完成时将完整历史来源与本轮 evidence 工具权限并集写入 ConversationDO.requiredTools。B 无新证据也保留 A 的访问约束，C 撤权后两个回答都隐藏。`AgentMessageDTO` 与 `AgentSnapshotDTO` 的唯一 canonical constructor 同时兼容旧 JSON 缺失 requiredPermissions：从 result.evidence 合并权限，不因字段缺失默认放行。
- 预算等待另覆盖分钟窗口额度先用尽而树 calls 仍小于 maxCalls 的情形：无 RUNNING 后代且有后代 BUDGET_EXHAUSTED 时也结束等待。依据是 `/tmp/v34-restart-diagnosis.log` 的明确失败；普通 interrupt 仍不产生完成通知，生产额度配置不改。
